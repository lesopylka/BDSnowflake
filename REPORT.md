## Модель данных

В `fact_sales` одна строка соответствует одной записи о продаже из исходных данных.

В таблице хранятся:

- количество проданных единиц `sale_quantity`
- сумма продажи `sale_total_price`
- ссылки на дату, покупателя, продавца, товар и магазин

Использована модель снежинка. Часть данных вынесена в отдельные справочники:

- страны и города в `dim_country` и `dim_city`
- тип и порода питомца в `dim_pet_type` и `dim_pet_breed`
- категория товара, бренд, цвет, размер, материал, категория питомца и поставщик в отдельные таблицы

Схема называется `star`, но по структуре это снежинка, так как измерения связаны с другими справочниками.

Для первичных ключей используются автоматически создаваемые ID. Исходные `id` и `sale_*_id` не используются как глобальные ключи.

Покупатели, продавцы, магазины и поставщики сопоставляются по email. При нескольких строках с одинаковым email в измерении сохраняется одна запись.

Для товара рассчитывается `product_nk` через MD5 по атрибутам товара и email поставщика. При изменении этих атрибутов получится другой ключ.

Сумму продажи из цены и количества не пересчитывала. В исходных данных есть расхождения, поэтому в модель перенесено значение `sale_total_price`.

## Проверка результата

Проверка выполняется скриптом [Scripts\check.sql](Scripts\check.sql).

Проверяются:

- количество строк в исходной таблице и таблице фактов
- общее количество проданных единиц
- общая сумма продаж
- наличие связанных записей для каждой продажи

После загрузки в обеих таблицах должно быть по 10000 строк.

| Таблица | Ожидаемое количество строк |
|--------|--------------------------:|
| `public.mock_data` | 10000 |
| `star.fact_sales` | 10000 |

Количество проданных единиц и сумма продаж должны совпадать с исходными данными. Значение `broken_links` должно быть равно 0.

Дополнительно выводятся 20 продаж с именами покупателей, названиями товаров и магазинов.

## Анализ исходных данных

Запросы находятся в [Scripts\analysis.sql](Scripts\analysis.sql).

В анализ входят:

## Конфигурация

В [docker-compose.yml](docker-compose.yml) настроен один сервис `postgres` с образом `postgres:15`.

Параметры подключения указаны прямо в compose-файле. Отдельные `.env` и сервис `migrate` не используются.

| Параметр | Значение |
|----------|----------|
| Контейнер | `bd_snowflake_db` |
| Хост | `localhost` |
| Порт | `5432` |
| База | `postgres` |
| Пользователь | `postgres` |
| Пароль | `postgres` |

Подключены следующие папки и том:

- `postgres_data` хранит данные PostgreSQL
- `./data` доступна внутри контейнера как `/data` только для чтения
- `./sql` доступна как `/docker-entrypoint-initdb.d`

## Запуск

Из папки с [docker-compose.yml](docker-compose.yml) выполнить команду:

```bash
docker compose up -d
```

При первом запуске с пустым томом PostgreSQL выполняет SQL-скрипты из папки `sql` в порядке имен.

Если база уже существует, автоматическая загрузка повторно не выполняется. Скрипты можно запустить вручную через DBeaver.

## Повторная загрузка

Скрипт создания модели добавляет недостающие таблицы, но не меняет структуру существующих.

Скрипт загрузки проверяет наличие 10000 строк в `mock_data`, очищает `fact_sales` и заново заполняет продажи. В справочники добавляются недостающие записи, существующие не обновляются.

Очистка и загрузка продаж выполняются в одной транзакции. При ошибке перед повторным запуском нужно выполнить:

```sql
ROLLBACK;
```

Для полного запуска с нуля можно удалить контейнер и том, затем запустить проект повторно. Это удалит все данные текущей базы.

```bash
docker compose down -v
docker compose up -d
```
