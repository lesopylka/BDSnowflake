# BigDataSnowflake
# Отчет лабораторной работы №1 - нормализация данных в снежинку

Работа выполнена студенткой МАИ группы М8О-205СВ-25 Суляевой Алиной Игоревной.

## Цель

Преобразовать исходные данные о покупателях, продавцах, поставщиках, магазинах и товарах для домашних питомцев в модель снежинка. Выделить таблицу фактов и таблицы измерений.

## Шаги выполнения

1. Подготовлен `docker-compose.yml` с PostgreSQL 15.
2. Исходные CSV размещены в папке `data`.
3. В папке `sql` размещены три init-скрипта с префиксами `01`, `02` и `03`.
4. Создана таблица `mock_data` для загрузки 10 файлов по 1000 строк.
5. Созданы таблицы модели снежинка в схеме `star`.
6. Подготовлена загрузка измерений и таблицы фактов `fact_sales`.
7. Добавлена связь породы питомца с его типом.
8. Подготовлены запросы для анализа данных и проверки результата.

## Модель данных

В `fact_sales` одна строка соответствует одной записи о продаже из исходных данных.

В таблице хранятся:

- количество проданных единиц `sale_quantity`
- сумма продажи `sale_total_price`
- ссылки на дату, покупателя, продавца, товар и магазин

Использована модель снежинка. Часть данных вынесена в отдельные справочники:

- страны и города в `dim_country` и `dim_city`
- тип и порода питомца в `dim_pet_type` и `dim_pet_breed`
- категория товара, бренд, цвет, размер, материал, категория питомца и поставщик в отдельные таблицы

Город связан со страной. Товар связан со справочниками характеристик и поставщиком.

Каждая порода связана с типом животного через `pet_type_id`. Уникальность определяется парой `(breed_name, pet_type_id)`. Одинаковые названия пород у разных типов животных сохраняются отдельно. При загрузке покупателя порода ищется по названию и типу питомца из той же строки CSV.

Связь отражает исходные данные. Она не проверяет, существует ли такая порода у указанного типа животного в реальности.

Схема называется `star`, но по структуре это снежинка, так как измерения связаны с другими справочниками.

Для первичных ключей используются автоматически создаваемые ID. Исходные `id` и `sale_*_id` не используются как глобальные ключи.

Покупатели, продавцы, магазины и поставщики сопоставляются по email. При нескольких строках с одинаковым email в измерении сохраняется одна запись. Разные сведения для одного email отдельно не сохраняются.

Для товара рассчитывается `product_nk` через MD5 по атрибутам товара и email поставщика. При изменении этих атрибутов получится другой ключ.

Сумму продажи из цены и количества не пересчитывала. В исходных данных есть расхождения, поэтому в модель переносится значение `sale_total_price`.

## Проверка результата

Проверка выполняется скриптом [Scripts\check.sql](Scripts\check.sql).

Проверяются:

- количество строк в исходной таблице и таблице фактов
- общее количество проданных единиц
- общая сумма продаж
- наличие связанных записей для каждой продажи

После загрузки в обеих таблицах должно быть по 10000 строк.

| Таблица | Ожидаемое количество строк |
|--------|--------------------------:|
| `public.mock_data` | 10000 |
| `star.fact_sales` | 10000 |

Количество проданных единиц и сумма продаж должны совпадать с исходными данными. Значение `broken_links` должно быть равно 0.

Дополнительно выводятся 20 продаж с именами покупателей, названиями товаров и магазинов.

Проверка связей подтверждает наличие записей в измерениях. Правильность объединения сущностей по email нужно оценивать отдельно. После изменения структуры пород проверки нужно повторить на заново созданной базе.

## Анализ исходных данных

Запросы находятся в [Scripts\analysis.sql](Scripts\analysis.sql).

В анализ входят:

- продажи и выручка по категориям товаров
- топ-10 стран покупателей по сумме покупок
- средняя сумма покупки по типу питомца
- среднее количество товара в одной продаже
- продажи по возрастным группам

## Конфигурация

В [docker-compose.yml](docker-compose.yml) настроен один сервис `postgres` с образом `postgres:15`.

Параметры подключения указаны прямо в compose-файле. Отдельные `.env` и сервис `migrate` не используются.

| Параметр | Значение |
|----------|----------|
| Контейнер | `bd_snowflake_db` |
| Хост | `localhost` |
| Порт | `5432` |
| База | `postgres` |
| Пользователь | `postgres` |
| Пароль | `postgres` |

Подключены следующие папки и том:

- `postgres_data` хранит данные PostgreSQL
- `./data` доступна внутри контейнера как `/data` только для чтения
- `./sql` подключена к `/docker-entrypoint-initdb.d` только для чтения

В папке `sql` находятся только три файла:

1. `01_start.sql` создает `mock_data` с текстовыми полями и загружает все 10 CSV.
2. `02_ddl.sql` создает таблицы снежинки в схеме `star`.
3. `03_dml.sql` заполняет измерения и таблицу фактов.

Скрипты `analysis.sql`, `check.sql` и `reload.sql` находятся в папке `Scripts`. Они запускаются вручную через DBeaver и не входят в первоначальную инициализацию.

## Запуск

Из папки с [docker-compose.yml](docker-compose.yml) выполнить команду:

```bash
docker compose up -d
```

При первом запуске с пустым томом PostgreSQL выполняет скрипты из `/docker-entrypoint-initdb.d` по порядку имен. Сначала загружаются CSV, затем создаются и заполняются таблицы модели.

Посмотреть ход загрузки и возможные ошибки можно командой:

```bash
docker compose logs -f postgres
```

После завершения загрузки нужно подключиться через DBeaver и выполнить `Scripts/check.sql`.

Если база уже существует, init-скрипты повторно не выполняются. Перезапуск контейнера и изменение файлов сами по себе не запускают загрузку заново.

## Повторная загрузка

Скрипт `02_ddl.sql` добавляет недостающие таблицы, но не меняет структуру существующих. Для перехода со старой таблицы пород на новую в этой работе используется полное пересоздание учебной базы.

Скрипт `03_dml.sql` проверяет наличие 10000 строк в `mock_data`, очищает `fact_sales` и заново заполняет продажи. В справочники добавляются недостающие записи, существующие не обновляются.

Очистка и загрузка продаж выполняются в одной транзакции. При ошибке перед повторным запуском нужно выполнить:

```sql
ROLLBACK;
```

Для повторной загрузки CSV в существующую таблицу используется `Scripts/reload.sql`. После него нужно выполнить `sql/03_dml.sql`, затем `Scripts/check.sql`.

Для полного запуска с нуля можно удалить контейнер и том, затем запустить проект повторно. Это удалит все данные текущей базы. CSV и SQL-файлы на компьютере сохранятся.

```bash
docker compose down -v
docker compose up -d
```

При новом запуске PostgreSQL снова выполнит `01_start.sql`, `02_ddl.sql` и `03_dml.sql`.
